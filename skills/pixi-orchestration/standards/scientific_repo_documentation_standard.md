## Project Documentation Standard (Scientific/Research)

When initializing a research repository or scientific project, you MUST strictly adhere to the following architectural guidelines to ensure a flawless chain of provenance from raw code to final paper.

### 1. The Locked Provenance Chain

Scientific validity requires an unbroken chain of custody for all claims. You must construct a Locked Provenance Chain, where manual edits or logic updates flow deterministically back and forth:

NaN) **Code & Data (Mutable):** Raw scripts, Jupyter notebooks, and raw datasets.

NaN) **ARA Evidence (Immutable):** Deterministic output (metrics, charts, logs) generated by the code.

NaN) **ARA Logic (Mutable):** The semantic arguments (`claims.md`, `problem.md`) derived from the evidence.

NaN) **Typst Report (Human Layer):** The final compiled PDF generated natively from `04_reports/paper.typ`. There is only ONE source of truth for the output document (`04_reports/paper.typ`).

**Backpropagation Rule:** If manual edits are made to the final Typst report, those changes MUST be backpropagated into the `ara/logic/` layer to keep the provenance chain synchronized. The `ara/` directory is the explicit, single source of truth for Machine-to-Machine (M2M) context. You MUST also copy the `AGENTS.md` template into the root of the repository to act as the standard entry point.

*(Note: The `research-manager` skill automatically handles the internal layout and updating of the `ara/` artifact. Do not attempt to manually format its internal files here).*

### 2. Holistic Folder Structure

When scaffolding a new scientific project, you MUST use the following holistic structure. We employ a "System vs User" split: User working directories are numbered chronologically (Cookiecutter Data Science pattern), while machine-managed workspaces are unnumbered to preserve tool integrations.

**User Working Directories (Numbered):**

- `01_scripts/` (or `01_src/`): Core execution code (Python, Rust, etc.).
- `02_notebooks/`: Jupyter notebooks for EDA and visualization.
- `03_data/`: Raw and processed datasets.
- `04_reports/`: The human-facing output folder. This is where the final compiled `.pdf` preprint, presentation slides, and standalone high-res `.svg` figures go when they are ready for publication.

**Machine Workspaces (Unnumbered):**

- `ara/`: The Agent-Native Research Artifact (managed by `research-manager`). This must remain unnumbered.
- `paperorchestra/`: The workspace for the PaperOrchestra compilation pipeline. This must remain unnumbered.

**Human Layer:**

- `README.md`: Executive summary, context, and physics/science intuition. Do **NOT** put deterministic execution strings (like `pixi run simulate`) or data schema breakdowns in the `README.md`.

### 3. Execution State (`pixi.toml` Tasks)

- Do **NOT** store complex, raw bash execution strings inside documentation files.
- **Instead**, define these strings natively in `pixi.toml` under the `[tasks]` section (e.g., `simulate = "bash 01_scripts/run_simulation.sh"`).

### 4. Continuous Housekeeping (Ultra-Granular Commits)

- **Snapshot Everything:** You MUST commit your changes continuously. Do not wait for a large "logical unit of work" to finish.
- **Triggers:** Every time you create a new script, generate a new result file, render a new figure, or make a meaningful change to an existing script, you must immediately snapshot the repository.
- **Action:** Trigger `MapWeaver` to update `CODEMAP.md`, then execute `git add .` and `git commit -m "..."`. This ensures we always have granular snapshots to revert to if a simulation fails.
